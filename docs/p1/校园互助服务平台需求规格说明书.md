**校园互助服务平台需求规格说明书**

**1\. 引言**

**1.1 目的**

本文档旨在定义"校园互助服务平台"的功能性和非功能性需求。基于对52名大学生的问卷调研和针对性的具体访谈结果分析，本平台不仅需满足快递代取、二手交易等基础互助需求，还需重点解决大学生的社交（找搭子）、情感（树洞）及学业组队需求，为开发团队提供设计与验收依据。

**1.2 范围**

本系统包含Web端与移动端，主要功能涵盖：**柔性实名认证**、**多模式互助发布**（跑腿/咨询/社交）、**积分与货币混合激励体系**、**社区互动**及**纠纷仲裁**。系统将服务对象限定为在校大学生，旨在构建安全、高效且具有温度的校园社区。

**1.3 定义、首字母缩写和缩略语**

- **柔性实名**：核心交易功能强制显示学号认证标识，社区/树洞功能支持匿名或昵称。
- **搭子**：指基于共同兴趣（如饭搭子、运动搭子）进行的临时组队。
- **经验分**：用户通过互助获得的非货币奖励积分，用于排行榜和等级晋升。
- **SRS**：软件需求规格说明书（Software Requirements Specification）

**2\. 总体描述**

**2.1 产品视角**

本系统是一个连接发布者与接单者的中介平台。与传统交易平台不同，本系统引入了"社区"与"激励"视角，不仅关注任务的完成，更关注用户在互助过程中的社交体验和成就感。

**2.2 用户特征**

- **主要用户（大学生）**：
    - **需求**：高频提及"跑腿（快递/食堂）"、"失物招领"、"找搭子"、"匿名树洞"。
    - **支付意愿**：约60%倾向免费或自愿捐款，反感强制高额手续费；对"经验值/成就感"敏感。
    - **隐私观**：支持学号认证防诈骗，但强烈要求部分板块（如树洞）具备匿名性。
- **次要用户（管理员）**：负责内容审核、纠纷仲裁及社区氛围维护。

**2.3 约束**

1.  **身份约束**：必须对接校园统一身份认证（CAS）以验证学籍，但允许用户设置昵称。
2.  **隐私约束**：严禁未经同意泄露用户手机号/学号，匿名板块需脱敏处理。
3.  **费用约束**：平台手续费率需极低或采用"自愿捐赠"模式，避免劝退用户。
4.  **合规性约束**：禁止代课等违反校规的行为，平台需设置内容审核机制。

**2.4 假设与依赖**

- 假设学校提供标准API接口用于学号真实性校验。
- 假设用户拥有智能手机并能接收短信/推送通知。
- 假设第三方支付（微信/支付宝）接口可用。
- 假设校园网络环境稳定，能够支持移动应用的正常运行。

**5\. 系统特性**

**5.1 系统架构概述**

系统采用前后端分离架构：

前端：Vue 3，TypeScript，Vite，Vue Router，Axios

后端：Java 17，Spring Boot 3.2.0，Spring Security，MyBatis-Plus，Starter + XML Mapper，MySQL，Redis，JWT，Maven

数据库：MySQL（关系型数据），Redis（缓存），MongoDB（非结构化数据）

部署：Docker容器化部署

**5.2 核心业务流程**

1.用户注册认证流程

2.任务发布接单流程

3.支付托管释放流程

4.评价仲裁处理流程

**7\. 其他需求**

**7.1 测试需求**

- **单元测试**：核心业务逻辑单元测试覆盖率不低于80%
- **集成测试**：验证各模块间接口兼容性
- **性能测试**：模拟高并发场景，确保系统稳定性
- **安全测试**：进行渗透测试，发现潜在安全漏洞
- **用户体验测试**：邀请目标用户进行可用性测试

**7.2 部署需求**

- **环境配置**：开发、测试、预发布、生产四套环境
- **备份策略**：每日全量备份+实时增量备份，保留7天
- **监控报警**：系统性能、业务指标、异常日志实时监控

**7.3 维护需求**

- **版本管理**：采用Git进行代码版本控制，遵循语义化版本规范
- **故障响应**：P0级故障响应时间≤1小时，P1级故障响应时间≤4小时
- **定期更新**：每月至少发布一次功能更新或安全补丁

**8.1 数据字典**
