## 2. AI 助力分析（Q1）

**编码中最有价值的场景**：快速生成 Controller / Service / DTO 样板代码，以及把重复性的接口、参数校验和基本 CRUD 骨架先搭起来。性能优化阶段，AI 能快速识别全表扫描、N+1、缓存设计缺陷等模式，并给出完整的 SQL 重写方案。

**测试生成中最有价值的场景**：补充边界条件和异常路径的初稿，例如分页不重叠、taskMode 互斥、缓存一致性等验证场景。

**调试中最有价值的场景**：面对性能问题（慢查询、缓存失效、N+1）时，AI 能从 SQL 执行计划、缓存策略、前端请求链多个维度同时分析，显著缩短定位时间。在 UNION ALL 替代 OR 条件这类 SQL 优化上，AI 的方案直接可用。

## 3. AI 误导分析（Q2）

**"AI 代码信任度实验"数据摘要**：
- AI 直出的测试通过率：约 60%
- 人工审查修复后的测试通过率：100%
- 发现的主要问题类型：权限校验遗漏、重复提交防护不足、积分/信用分结算逻辑过度理想化、密码哈希泄露、JWT token type 缺失、注册限频绕过

**"AI 调试对决"实验总结**：
- AI 擅长调试的 Bug 类型：配置缺项、字段映射冲突、条件分支遗漏、旧数据归一化问题、慢查询模式识别
- AI 不擅长调试的 Bug 类型：需要结合课程验收标准或工程取舍的复杂判断题
- AI 修复方案的典型问题：容易只修表象，不主动追问根因与业务约束

**性能优化中的新发现**：AI 在性能诊断中表现出色——能快速识别 "OR 不走索引""单 key 缓存全表""N+1 请求"等模式。但 Redis 序列化兼容问题（GenericJackson2JsonRedisSerializer 不支持 INCR）这类框架细节，AI 的初始方案需要人工修正。

## 4. Prompt 改进计划（Q3）

**上阶段改进措施的验证结果**：要求 AI "基于当前项目现有结构和真实验证结果输出"，比单纯让它"按文档生成报告"更有效，能显著减少空泛内容。

**编码阶段的 Prompt 最佳实践**：先明确模块边界、输入输出和异常规则，再让 AI 生成局部代码。对于性能优化，先提供 EXPLAIN 结果和慢查询日志，再让 AI 给方案。

**调试阶段的 Prompt 最佳实践**：同时提供报错信息、复现步骤、相关代码片段和期望行为；涉及数据库时附上 EXPLAIN 和索引信息。

**下阶段计划改进**：如果进入 P5 测试与交付阶段，应要求 AI 同时输出"结论 + 证据 + 未满足项"，避免它把"存在文件"误写成"验收已完成"。

## 5. 本阶段的核心工程判断

**决策内容**：在 P4 后期发现性能严重影响可用性时，决定暂缓新功能开发，集中做一轮性能优化（分页、索引、缓存重构、SQL UNION ALL、轮询优化）。同时把 `dev` 分支作为 P4 的真实代码基线，不以文档虚构成果。

**为什么 AI 无法单独做这个决策**：AI 能识别性能问题模式，但它不会评估"课程验收截止时间 vs 继续优化的边际收益"。它天然倾向于不断提出更多优化建议，而人工需要判断"做到什么程度够交"。安全审计中，AI 能发现漏洞模式，但"是否需要移除第三方登录"这类产品决策需要人工判断。

**团队最终如何判断和取舍**：先以 `dev` 分支实际代码、测试和 CI 为准，确保 P0/P1 可用、性能可达演示标准。再把已完成、基本完成和未满足项分开记录，保证 P4 材料既能提交，也不掩盖真实差距。
