## 2. AI 助力分析（Q1）

AI 在编码中最有价值的场景：快速生成 Controller / Service / DTO 样板代码，以及把重复性的接口、参数校验和基本 CRUD 骨架先搭起来。

AI 在测试生成中最有价值的场景：补充边界条件和异常路径的初稿，例如重复评价、越权完成、模式冲突兼容等场景的测试样例。

AI 在调试中最有价值的场景：面对配置缺项、字段不一致、旧数据兼容这类问题时，能快速提供候选根因和排查顺序，显著缩短定位时间。

## 3. AI 误导分析（Q2）

"AI 代码信任度实验"数据摘要：

- AI 直出的测试通过率：`约 60%`
- 人工审查修复后的测试通过率：`100%`
- 发现的主要问题类型：权限校验遗漏、重复提交防护不足、积分/信用分结算逻辑过度理想化、密码哈希泄露、JWT token type 缺失、注册限频绕过

"AI 调试对决"实验总结：

- AI 擅长调试的 Bug 类型：配置缺项、字段映射冲突、条件分支遗漏、旧数据归一化问题
- AI 不擅长调试的 Bug 类型：需要结合课程验收标准或工程取舍的复杂判断题
- AI 修复方案的典型问题：容易只修表象，不主动追问根因与业务约束

## 4. Prompt 改进计划（Q3）

上阶段改进措施的验证结果：要求 AI “基于当前项目现有结构和真实验证结果输出”，比单纯让它“按文档生成报告”更有效，能显著减少空泛内容。

编码阶段的 Prompt 最佳实践：先明确模块边界、输入输出和异常规则，再让 AI 生成局部代码，而不是直接让它完成整块业务。

调试阶段的 Prompt 最佳实践：同时提供报错信息、复现步骤、相关代码片段和期望行为；如果还涉及课程或业务规则，也要一并给出。

下阶段计划改进：如果进入 P5 测试与交付阶段，应要求 AI 同时输出“结论 + 证据 + 未满足项”，避免它把“存在文件”误写成“验收已完成”。

## 5. 本阶段的核心工程判断

决策内容：把 `dev` 分支作为 P4 的真实代码基线，以此补齐文档与验收材料，而不是在 `p4` 分支重新虚构一套”看起来完整”的阶段成果。同时在 P4 阶段进行安全审计，修复了 7 个 CRITICAL 级漏洞。

为什么 AI 无法单独做这个决策：因为这不是文本生成问题，而是工程真实性问题。AI 会天然倾向于根据任务说明补齐”理想答案”，但只有人工会优先追问：代码到底在哪个分支、哪些验证是真跑过的、哪些验收项只是看起来有文件。安全审计中，AI 能发现漏洞模式，但”是否需要修复第三方登录”这类产品决策需要人工判断。

团队最终如何判断和取舍：先以 `dev` 分支实际代码、测试和 CI 为准，再把已完成、基本完成和未满足项分开记录，保证 P4 材料既能提交，也不掩盖真实差距。安全方面，团队决定移除第三方登录（不再维护）、引入 UserVO 防密码泄露、添加 JWT token type claim 防止 token 混用，并在 SecurityConfig 中保护管理员路径。
