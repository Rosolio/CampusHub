# AI 代码信任度实验报告

## 1. 实验目标

选择“评价提交与积分/信用分更新”作为实验功能点，观察 AI 生成业务代码时的可用性与局限。

选择该功能的原因：

- 既包含基础 CRUD，也包含业务规则
- 同时涉及任务状态、评价唯一性、积分、信用分等多个对象
- 容易暴露“看似能跑，实则规则不严谨”的问题

## 2. 实验对象

- 功能点：`TaskReviewService.createTaskReview`
- 关联模块：`TaskService`、`UserService`、`TaskReviewMapper`、`UserPointRecord`

## 3. AI 直接生成 Prompt 摘要

```text
请为校园互助平台实现任务评价功能：
1. 仅任务参与者可评价
2. 同一用户对同一任务只能评价一次
3. 双方完成任务后才能评价
4. 提交评价后更新被评价人的信用分
5. 根据评分发放或扣减积分
6. 给出 Java Spring Boot Service 层实现
```

## 4. AI 直出结果摘要

AI 能较快生成以下骨架：

- 校验任务是否存在
- 插入评价记录
- 计算平均分并回写用户信用分
- 根据评分做简单积分变更

但初始版本容易出现两个典型问题：

1. 只校验“任务存在”，没有严格校验“当前用户是否为任务参与者”
2. 只实现“加分”，忽略低分评价的扣分或惩罚逻辑

## 5. 人工检查点

按 P4 要求，人工重点检查以下 3 项：

### 5.1 是否符合 P3 详细设计

- 是否只允许任务双方互评
- 是否以“双向完成”为前置条件
- 是否符合评价与信用体系设计

### 5.2 是否覆盖常见异常或边界情况

- 重复评价
- 非参与者评价
- 低分评价
- 评价后重复结算积分

### 5.3 是否存在明显 Bug 或不合理逻辑

- 评价完成即直接成功，未考虑另一方尚未评价
- 信用分更新只取当前评分，而不是聚合历史评分
- 积分奖励与惩罚缺乏可解释性

## 6. 发现的主要问题

| 问题 | AI 直出表现 | 人工修复方向 |
|---|---|---|
| 权限校验不足 | 可能只基于任务 ID 判断 | 增加任务参与者身份校验 |
| 唯一性约束不完整 | 容易遗漏“同一用户不可重复评价” | 依赖业务校验 + 唯一索引双保险 |
| 结算逻辑过于理想化 | 只奖励不惩罚，或只按单次评分回写信用分 | 引入平均分与低分扣分规则 |

## 7. 修复后对应证据

从 `dev` 分支现有测试可看到修复后的行为已被验证：

- `TaskReviewTest.testCreateDualReviewsAndUpdateScore`
- `TaskReviewTest.testCannotReviewSameTaskTwice`
- `TaskReviewTest.testLowStarReviewCanDeductRevieweePoints`

## 8. 实验记录表

| 指标 | AI 直出 | 人工审查修复后 |
|---|---|---|
| 编译是否通过 | 大概率可通过 | 通过 |
| 功能是否可运行 | 可运行，但规则可能不完整 | 可运行 |
| 测试是否通过 | 无法保证 | 通过 |
| 主要问题/修复说明 | 权限、唯一性、积分结算易失真 | 已用测试约束关键业务规则 |

## 9. 结论

这类功能点说明：AI 非常适合快速产出 Service 骨架和样板代码，但不能直接信任其业务正确性。越是涉及状态、权限、积分、信用分这类跨实体规则，越需要人工把控。
