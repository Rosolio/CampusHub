# Sprint 合并任务看板

## 1. 规划原则

- 以 P0 能跑通完整主流程为第一优先级
- P1 功能做到“基本可用”，但不以牺牲主流程稳定性为代价
- 单个任务控制在 2-4 小时量级，便于并行推进
- 结合 `dev` 分支现有实现，状态分为：已完成、基本完成、待补强

## 3. 必须进入本阶段交付的内容

### 3.1 必须保底

- 用户注册与登录
- 任务发布、列表、详情
- 接单、完成、状态流转
- 消息通知
- 评价提交
- 基础测试可运行（70 个测试通过）

### 3.2 可以接受“基本可用”的内容

- 后台管理页的交互细节
- 反馈/仲裁的复杂升级策略
- 更精细的通知模板与去重策略

## 4. 风险识别

| 风险类型   | 说明                   | 当前判断                          |
|--------|----------------------|-------------------------------|
| 集成风险   | 前后端字段或状态枚举不一致        | 已通过前后端接口命名和页面路由初步收敛，但仍需人工演示验证 |
| 测试环境风险 | 后端测试依赖 MySQL 与 Redis | 本次验证环境可运行，助教环境需按 README 准备    |
| CI 风险  | GitLab 配置已补齐，但仍需在平台侧跑一次正式流水线留档 | 主要剩余问题是证据沉淀，不是配置缺失 |
| 覆盖率风险  | 已生成 JaCoCo 报告，当前行覆盖率为 `61.45%` | 风险已基本消解 |

## 5. 工程判断

本阶段最关键的取舍不是“继续加功能”，而是把现有主流程、测试和部署说明做实。`dev` 分支现状说明团队已经完成主要编码任务，但如果不补足 CI 与覆盖率证据，验收时会在“质量保障”项上吃亏。
